# food-delivery-notification-service

Сервис платформы доставки еды. Платформа целиком (docker-compose, наблюдаемость, Postman,
общая документация) — в репозитории [food-delivery-platform](https://github.com/Dima77726/food-delivery-platform);
контракты событий, gRPC и REST — в [food-delivery-contracts](https://github.com/Dima77726/food-delivery-contracts).

## Сборка

Контракты лежат в GitHub Packages, а он требует токен даже для чтения. Один раз в
`~/.m2/settings.xml`:

```xml
<servers>
  <server>
    <id>github</id>
    <username>ВАШ_GITHUB_ЛОГИН</username>
    <password>ТОКЕН_С_ПРАВОМ_read:packages</password>
  </server>
</servers>
```

```bash
./mvnw verify
```

Интеграционным тестам нужен Docker (Testcontainers).

## Образ

```bash
docker build --secret id=maven_settings,src=$HOME/.m2/settings.xml -t food-delivery-notification-service .
```

CI публикует образ в `ghcr.io/<владелец>/food-delivery-notification-service` на каждый пуш в `main` и `dev`.

## Доставка по e-mail

По умолчанию уведомления уходят «в лог». С `EMAIL_ENABLED=true` канал EMAIL отправляет настоящие
письма по SMTP; SMS и PUSH по-прежнему остаются в логе — у них нет шлюза.

```
событие заказа → уведомление (PENDING) → задача в RabbitMQ → работник:
    gRPC identity-service: GetUserContact(userId)  →  адрес, имя, «включён»
    SMTP: письмо  →  уведомление SENT
```

- **Адреса в событии нет.** Событие заказа читают многие потребители, а адрес — персональные
  данные, поэтому сервис знает получателя по номеру и спрашивает контакт у identity-service в
  момент отправки. Цена — зависимость от него; её смягчают повторы очереди и предохранитель на
  канале. Копия адресов в этом сервисе была бы независимее, но это второй источник персональных
  данных, который нужно синхронизировать и чистить.
- **Постоянная и временная ошибки.** Получателя нет, он заблокирован, адреса нет —
  `PermanentDeliveryException`: уведомление сразу `FAILED` с причиной, без пяти кругов через очередь
  ожидания. Недоступный SMTP или identity-service — временная ошибка, задача уходит на повтор
  (`NOTIFICATION_MAX_ATTEMPTS`, пауза `NOTIFICATION_RETRY_DELAY`).
- **«Хотя бы один раз».** Отправка идёт внутри транзакции доставки: если SMTP принял письмо, а
  коммит не удался, письмо уйдёт повторно. «Ровно один раз» без распределённой транзакции
  невозможно, и выбор сделан в пользу повтора, а не потери.
- **mTLS.** В docker-compose канал к identity-service идёт по взаимному TLS (профиль `grpc-tls`),
  identity-service пускает сервис по имени `notification-service` из сертификата.
- В лог адрес не пишется, только номер пользователя.

Настройки: `MAIL_HOST`/`MAIL_PORT` (по умолчанию `localhost:1025`, это Mailpit из compose),
`MAIL_USER`/`MAIL_PASSWORD`/`MAIL_AUTH`/`MAIL_STARTTLS` для настоящего SMTP-провайдера,
`EMAIL_FROM`, `IDENTITY_GRPC_ADDRESS`. Письма локально видны в интерфейсе Mailpit:
http://localhost:8025.

## Уведомления в Telegram

Второй настоящий канал рядом с почтой. Включается `TELEGRAM_ENABLED=true` и токеном бота; без них
сервис работает как раньше и ни токена, ни имени бота не требует.

### Подключить бота

1. В Telegram откройте [@BotFather](https://t.me/BotFather), команда `/newbot`, получите **токен**
   и имя бота.
2. В `.env` платформы: `TELEGRAM_ENABLED=true`, `TELEGRAM_BOT_TOKEN=…`, `TELEGRAM_BOT_USERNAME=имя_бота`
   (без `@`). Токен — секрет: по нему можно писать от имени бота кому угодно, в репозиторий он не попадает.
3. Перезапустите notification-service.

### Как пользователь подключает Telegram

```
POST /api/v1/notifications/telegram/link   →  { "deepLink": "https://t.me/<бот>?start=<код>", "expiresAt": … }
```

Пользователь открывает ссылку в Telegram и нажимает «Запустить». Бот получает `/start <код>`, находит
пользователя по коду и запоминает чат. Дальше уведомления о его заказах приходят и по почте, и в
Telegram. `GET /api/v1/notifications/telegram` — подключён ли; `DELETE` или команда `/stop` в чате — отключить.

- **Код одноразовый**, живёт 15 минут и хранится только хэшем (SHA-256): утечка таблицы не позволит
  привязать чужой аккаунт. Новый запрос отменяет прежний код.
- **Один чат — один пользователь.** Привязка чата к другому пользователю снимает её у прежнего:
  иначе чужие уведомления попадали бы в чужую переписку.
- **Только личная переписка.** В группах и каналах бот молчит и ничего не привязывает: `/start`
  мог бы отправить любой участник.

### Как это работает

- **Long polling, не вебхук.** Вебхуку нужен адрес, доступный из интернета, а у локального стека его
  нет. Бот опрашивается своим потоком (не планировщиком Spring: опрос блокируется на десятки секунд и
  остановил бы остальные задачи). Позиция опроса хранится в базе, поэтому после перезапуска
  уже обработанные сообщения не приходят снова.
- **Опрос ведёт один экземпляр.** Второй получит от Telegram 409 и будет ждать. На лишних
  экземплярах — `TELEGRAM_POLLING_ENABLED=false`; отправка уведомлений от опроса не зависит.
- **Каналы независимы.** Идемпотентность держит пара «событие + канал» (миграция `002`), поэтому
  повтор события не дублирует доставленное по одному каналу и не мешает поставить недостающее по другому.
  Telegram-уведомление создаётся только тем, у кого есть привязка.
- **Постоянная и временная ошибки.** Бота заблокировали (403) или чата нет (400 «chat not found») —
  привязка снимается, уведомление сразу `FAILED`, без пяти кругов через очередь. Любой другой 400 (скажем,
  слишком длинный текст) привязку **не** снимает: иначе ошибка в нашем сообщении отвязывала бы живого
  пользователя. 429, 5xx и сеть — временные, очередь повторит.
- **Токен не попадает ни в лог, ни в трассы.** Он стоит в пути запроса Bot API, поэтому клиент
  собран без наблюдаемости (спан записал бы полный адрес), а тексты ошибок очищаются от токена
  в том числе в URL-кодированном виде.
- Текст уходит обычный, без разметки: тема и тело приходят из событий и могут содержать любые
  символы, а ошибка экранирования роняла бы сообщение целиком.

### Диспетчер каналов

Отправитель канала — `ChannelNotificationSender`; `RoutingNotificationSender` выбирает его по
каналу уведомления. Канал без отправителя (выключенный флагом, а также SMS и PUSH, у которых шлюза нет)
уходит «в лог», как и раньше. Два отправителя на один канал — ошибка при старте.
